# Milestone 2 discovery analysis

The modular monolith keeps its domain unchanged. `application/analysis_models.py`
defines immutable review proposals using the domain claim and assumption enums.
`application/discovery_analysis.py` owns `AnalysisInput`, `AnalysisProvider`, the
orchestrating service and deterministic context checks. `AnalysisRecord` retains the
complete request, result, analysis timestamp and provider/model/prompt version metadata;
callers must retain this record themselves. It is an analysis artifact, not a domain
mutation audit event. The service performs no storage or lifecycle transitions.

The flow is submission + optional configured strategy + existing domain knowledge →
provider → Pydantic result revalidation → source/category/strategy checks → review result.
`infrastructure/openai_analysis.py` implements OpenAI Responses `responses.parse` with
`text_format=DiscoveryAnalysis`, using SDK-generated strict JSON Schema. Refused,
incomplete and invalid responses fail clearly. The client uses a 60-second timeout,
up to two SDK retries for transient transport/rate-limit/server failures, and `store=False`.
Validation failures and refusals are not retried. API exceptions become safe application
errors; unexpected adapter errors are contained by the application service.

## Structured interpretation

Twelve intake classifications cover observation through technical signal and other.
Each normalization field is either a hypothesis or explicit unknown. Separate arrays
contain fact/evidence/inference/unknown proposals and rich assumption proposals.
Cross-field validation enforces category placement, unique IDs, valid contradiction
references, a riskiest assumption and validation targeting that assumption. Assumptions
include decision relevance and ordinal importance/uncertainty. Validation recommendations
include method, required input, success/failure signals, relative cost/speed and cheaper
alternatives considered. Strategic-fit output contains objective references, alignment,
conflicts and explanation; no deterministic score is calculated.

Pydantic schemas intentionally have no omitted output fields. Arrays use tuples in the
validated result so nested proposals are immutable. All AI proposals are explicitly
`agent_generated=True`; this labels interpretation, including exact source restatements.
It does not claim the external underlying source was generated by AI.

Facts must match a supplied existing FACT claim exactly, with a matching source citation.
Evidence must match supplied non-invalidated domain Evidence exactly. These categories
cannot be exchanged. Free-text submissions cannot establish facts or evidence, even
when they contain confident numbers. The model can preserve them as assumptions or
inferences until reviewed. Citation excerpts must occur in the specified input source.
Invalidated evidence can inform competing interpretations but cannot become active evidence.
Strategy references must identify the configured objective; missing or Unknown objectives
require insufficient_strategy_context with no alignment/conflict assertions.

`application/analysis_mapping.py` explicitly maps a reviewed assumption proposal into the
existing domain Assumption model, retaining underlying source and submission provenance,
AI-generation tagging, and rationale/decision relevance. The caller supplies identity.
AI-summary-only provenance is rejected. There is no automatic fact/evidence promotion,
persistence, linking, human approval workflow, audit mutation or lifecycle transition.

## Prompts and configuration

`ai/prompts.py` separates versioned system interpretation instructions from JSON-encoded
input. Original text is preserved exactly in the encoded request. Source text is treated
as untrusted data; instructions explicitly reject embedded prompt instructions. The output
schema lives in application code. Deterministic policy lives outside prompts.

Install the pinned development dependencies and package as documented in README.
For live usage, set `OPENAI_API_KEY` and `DISCOVERY_ANALYSIS_MODEL` to an account-accessible
model supporting Responses structured output. `.env.example` is documentation; the
application does not automatically load .env files. No model or key is hard-coded.

```python
from datetime import UTC, datetime
from product_discovery_engine.application.discovery_analysis import (
    AnalysisInput,
    DiscoveryAnalysisService,
)
from product_discovery_engine.infrastructure.openai_analysis import (
    OpenAIAnalysisConfig,
    OpenAIAnalysisProvider,
)

config = OpenAIAnalysisConfig.from_environment()
provider = OpenAIAnalysisProvider(config)
service = DiscoveryAnalysisService(provider)
# submission is an existing immutable domain Submission; policies is optional.
request = AnalysisInput(submission=submission, strategy=policies.strategy)
record = service.analyze_record(
    request,
    analyzed_at=datetime.now(UTC),
    provider="openai",
    model=config.model,
    prompt_version=provider.prompt_version,
)
# Retain record for review; nothing is written to the knowledge model automatically.
```

Provider-neutral callers can implement `AnalysisProvider.analyze` with any validated
result producer; the application imports neither OpenAI nor infrastructure.

## Verification and limits

Run `.venv/bin/python -m pytest` for the complete offline suite. Run
`.venv/bin/python -m pytest tests/evals -m 'not live_ai'` for golden contracts.
Paid live verification is intentionally deferred by project decision and is not required
for normal CI, milestone completion or merge. `OPENAI_API_KEY` is optional for development.
Track later-phase checks in the [project checklist](../evals/deferred-live-verification.md).
Deferred or skipped live verification does not establish semantic quality.
For that later authorized phase, live evaluation requires credentials, an allowed API
destination and explicit opt-in:
`RUN_LIVE_AI_EVALS=1 .venv/bin/python -m pytest tests/evals -m live_ai`.
Normal tests do not make live calls even if credentials happen to exist.
The ten fixtures cover solution requests, unsupported numbers, mixed problem/solution,
missing strategy, conflicting explanations, explicit unknowns, generated assumptions,
causality, anecdotes, and early discovery validation. They are representative human-written
review examples, not a deterministic substitute for an LLM. Offline tests verify contracts
and rejection behavior; live tests verify broad behavior separately. SDK integration tests
use httpx mock transport with the real parser for valid, invalid, refused, incomplete,
authentication and rate-limit responses.

Structural validation cannot certify source authenticity, semantic entailment of inferences,
completeness of extracted contradictions, correct strategy interpretation or optimal choice
of validation method. Existing FACT classifications must be reviewed upstream; exact
restatement preserves an existing classification rather than independently proving it.
Ordinal risk and validation cost/speed are AI recommendations, not scored policy. Schema
validation alone cannot prevent prompt injection. Human review remains essential.

Current limitations: one strategy objective in the existing policy model; synchronous calls;
no durable persistence, deduplication, concurrency protection, context-size budgeting,
source fetching, application UI or automated knowledge acceptance. Full records may contain
sensitive source text, so production retention/access policy is still required. `store=False`
does not define the provider's full data retention policy. Model versions may drift;
record metadata and track model/prompt changes for reverification during the later
authorized live phase.

Milestone 3 evidence evaluation and validation are now implemented; see
[evidence and validation](evidence-validation.md). Readiness gates, deterministic
prioritization/scoring and Milestones 4–7 remain unimplemented.
